# 未修改 CK 完整客户端的 HCC 适用性

样本沿用 P2 预先冻结的 **1 个**完整上游 event-counter smoke-test 客户端，
不是生产应用，也不是“上游例程加自建 harness”。保留原始
`regressions/ck_ec/validate/ck_ec_smoke_test.c`、`src/ck_ec.c`、类型、配置及
Makefile 编译参数。没有换样本、删循环/回调/系统调用、改写 asm 或造 Q。
上游提交仍是 `8f0847cfe57b1479d8e63b89028831d94d0e4d26`。

本轮重新检查原始文件、所有依赖、两份实际同次 AST/LLVM 捕获的哈希；
两 TU 分别保留 80、33 个存活 LLVM asm。它们并不都属于本原型接受的 FAA
调用接口，不能把“113 个 asm”写成“113 个已认证 asm”。原完整客户端的条件式
程序认证仍为 **0/1**。[机器可复核审查](../../experiments/hcc/external-client-review.json)

需要的可复用契约不是每条 C 语法一个特例，而是以下语义接口：

| 接口 | 具体需要保证的内容 | 当前依据 |
|---|---|---|
| 对象与类型 | 聚合对象字段、生命周期、别名、普通/asm 冲突排除 | 没有完整宿主证明 |
| 链接与调用 | 两 TU 的实际链接、直接/间接调用及回调的类型化输入输出 | 只有真实编译捕获；无语义桥接证书 |
| wait/wake 与时钟 | `ops->wait32/wake32` 等调用、futex/系统调用、时间和错误返回的开放语义 | 不能由原受限 pthread Γ_runtime 自动涵盖 |
| 循环与重试 | phase/对象不变式、每次 asm 出现的新身份、任意有限错误前缀 | 无归纳 provider；不可用固定展开替代 |
| 全局内存与排序 | 全部共享效果、原子性、Fence、跨回调/线程顺序及统一 rf/co | 不能只拿 FAA 局部等价补齐 |
| 用户错误与查询 | 原断言/失败前缀、实际 Q/property/bound 与求解结果对应 | 未生成可认证整程序 Q，故未运行该客户端后端 |

`main(int,char**)`、多 TU 或某个 AST 节点不被当前工具识别，是**工具范围障碍**。
单独扩展这些解析规则不能解决以上**定理适用前提缺失**。特别是原 Γ_domain
和 Γ_runtime 只支持已有的成功 pthread 生命周期与有限宿主；将全部 OS 行为
直接纳入一个新“可信 HCC”会增加语义 TCB。本轮没有这样做。

在一个独立的受控分支 harness 上还观察到更具体的实现障碍：Clang 把条件输入
编译为真实 `select`，原 Dat3M 能运行并输出 PASS，但当前只读导出器不能完整
序列化 `ITEExpr`，捕获门禁拒绝。保留原始前后序列化、查询审计与日志；它们是
**不完整导出**，不是已认证 Q。即使以后补齐导出，也仍须补足宿主 HCC。
[原始观察](../../experiments/hcc/branch-backend-01/observation.json)

因此，Scheme A 目前能够清晰定位欠缺的语义接口，却尚未给这个完整客户端
提供可满足的外部契约。不能以改变契约名称代替建立这些依据。
